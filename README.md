# maxed-agent

A drafting agent that writes a client message explaining an account balance due, checks its own
draft against the real ledger records, and lands on exactly one of revise, abstain, or escalate.
Every human decision on a draft is captured as structured signal, and a retrieval-memory mechanism
uses that signal to guide future drafts automatically.

Current status: Part 1 (self-checking agent) and Part 2 (learning loop) are built and tested.
Part 3 (the eval harness) is not implemented yet.

## Setup

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env
```

`.env` controls `MODEL_PROVIDER`: `stub` (default, canned responses, zero credentials and no
network), `ollama` (local model via an OpenAI-compatible endpoint), or `gemini` (hosted, also
OpenAI-compatible). A local Ollama model is the intended way to run this for real; `gemma2:9b` is
the default and `gemma2:2b` is noted as a faster fallback in `.env.example`.

## Commands

```bash
pytest                        # full test suite, stub mode, no model or network needed
maxed-agent generate          # one generate -> verify -> decide cycle against the fixture ledger
maxed-agent injected-errors   # Part 1 proof: corrupts drafts on purpose, reports caught vs missed
maxed-agent learning-cycle    # Part 2 proof: batch (no memory) -> decide -> ingest -> batch (with memory)
```

All three commands take `--client-id`, defaulting to `CLIENT-001` (`CLIENT-002` is the second
fixture client).

## What was built

**Fixtures.** Two synthetic clients, each with their own ledger (`src/maxed_agent/fixtures/`),
generated by a deterministic script, not hand-typed. CLIENT-001 (28 transactions, balance
$1,337.50) and CLIENT-002 (20 transactions, balance $735.00). Transaction ids are globally unique
across both ledgers (CLIENT-002's start at TXN-029) specifically so a leaked cross-client reference
is unambiguous to detect. Each balance is computed by summing the transactions in code and is the
single source of truth the verifier checks against.

**Part 1, the self-checking agent.** `generator.py` prompts the model to write the client message
and requires every transaction to be mentioned, with its transaction id cited next to its dollar
amount, ending in a fixed `Total balance due: $X` line. `verifier.py` is pure code, no second model
call: it regex-extracts every cited transaction id and dollar amount and checks each one against
the ledger directly. `loop.py` revises up to twice, then lands on escalate (a real transaction
exists but a number is off, a human can quickly confirm the fix) or abstain (the claim has no
supporting record at all, a human correction would not be a quick confirmation). `injected-errors`
proves the verifier has teeth: it deliberately corrupts a clean draft with a wrong amount, a
fabricated transaction, an unsupported claim, and a wrong total, and confirms all four are caught
alongside a clean control that produces no false positive.

**Part 2, the learning loop.** `decision_log.py` defines the structured records (pydantic, not raw
dicts): a `DecisionRecord` per draft (source context, draft, critique, human decision, final text)
and a `CapabilityGapRecord` whenever the agent abstains or escalates, capturing what it would have
needed to succeed. `human_sim.py` plays the human: approves, edits and approves, or declines.
`retrieval_memory.py` is the consumption mechanism (see below), scoped per client id: retrieving
examples for one client never returns another client's approved drafts, verified by a test that
runs the real learning cycle for both clients against one shared, unreset decision log and checks
that no transaction id from client 1's ledger ever appears in client 2's injected memory.
`learning-cycle` runs a batch with no memory, logs decisions, builds memory from the qualifying
approved examples, then runs a second batch with that memory injected as few-shot guidance, and
reports both batches' outcomes side by side.

## Consumption mechanism: retrieval memory, and why

Of the three defaults the brief names (retrieval memory, prompt-patching from failure patterns, a
preference dataset for a future fine-tune), retrieval memory was the only one where the core test
(`run, decide, ingest, run again, the second batch should differ in the direction the decisions
pointed`) is directly observable in the next generation call, with no extra machinery. Prompt-
patching risks overfitting a prompt edit to a handful of examples with no real validation step in
the time available. A preference dataset's payoff is inherently indirect, it proves the data is
well-formed, not that behavior changed, and the brief itself treats an actual fine-tune pass as
stretch, not core. Retrieval memory is also the cheapest mechanism to imagine landing first in a
real system like Maxed's: no retraining infrastructure, fast to iterate, easy to inspect.

## Assumptions

- Two synthetic clients, each with their own ledger, is the whole scope for this build; the brief
  allows one or two.
- "Grounded" is treated as: every dollar amount and every transaction reference in the draft must
  match the ledger exactly. The generation prompt requires citing a transaction id next to every
  amount specifically so this is checkable by regex and lookup, not by asking a model to judge its
  own arithmetic.
- The human simulator is a fixed, documented policy, not a model of real human judgment: approve
  outcomes that cite at least one real transaction get approved (sometimes with a small cosmetic
  edit), sparse outcomes that cite none get declined even though the verifier found no false claim
  in them, escalate outcomes get every correctable issue fixed and approved with an edit note,
  abstain outcomes get declined with a capability-gap record.
- Abstain versus escalate is a fixed rule for this build (fabricated or unsupported claims abstain,
  a real record with a wrong number escalates), not a learned or calibrated policy. The brief lists
  calibrating this boundary as stretch.

## What was cut, and why

- A second artifact type (the account summary or the document follow-up) was not built. The brief
  is explicit that depth on one artifact beats shallow coverage of more, and Part 2 and Part 3 are
  where the brief says most systems fail, so time went there instead.
- Retrieval in `retrieval_memory.py` is scoped by client id (never crosses clients, see below) but
  recency-based within a client, not similarity-scored. With a single artifact type per client
  there is nothing to be similar to yet beyond recency; a real system with multiple artifact types
  per client would need actual similarity scoring, and that is noted here rather than built for a
  scope that does not exist yet.
- Part 3 (the judge, calibration against a hand-labeled set, a defended judge failure mode, the
  before/after score comparison) has not been started.
- Fine-tuning or DPO on the captured decisions was not attempted; the brief lists this as stretch,
  never the bar.

## Blind spots

- The verifier only catches claims that resolve to a dollar amount. A qualitative fabricated claim
  with no number attached (for example, a made-up statement about an account flag or a policy) would
  not be caught by anything in Part 1. This is a real gap, not a hypothetical one.
- The verifier checks grounding, not completeness or tone. A draft can cite every transaction
  correctly and still be a bad client message in other ways; that is explicitly left for Part 3's
  judge, but until Part 3 exists there is no check for it at all. Two real bugs during this build
  came from exactly this gap: a model that produced a nearly content-free but technically "grounded"
  draft, and a model that leaked internal revision feedback into a factually correct draft. Both
  are now caught by targeted checks (a minimum-citation floor and a leaked-text marker), but the
  general category, anything wrong with a draft that not is a false factual claim, is not
  exhaustively covered.
- The learning-cycle proof so far uses a batch size of 3 per side, run live against gemma2:2b for
  speed. That is enough to demonstrate the mechanism runs correctly end to end and does not corrupt
  itself on bad examples, but it is too small a sample to support a strong quantitative claim either
  way about whether retrieval memory reliably improves output. The most recent live run showed no
  measurable difference between batches; an earlier run (before two real bugs were fixed) showed an
  apparent improvement that further inspection showed was not real. Both results are recorded in
  `DECISION_JOURNAL.md`.
- The sentence-level checks in the verifier are regex-based against real but limited model output
  so far. Two genuine edge cases were found and fixed during this build (a punctuation-dependent
  sentence merge, and newline-formatted bulleted lists breaking the same assumption); more exist and
  have not been stress-tested, for example a dollar amount landing exactly at a sentence boundary
  with ambiguous punctuation.
