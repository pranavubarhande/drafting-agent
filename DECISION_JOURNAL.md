# Decision journal

- Chose the client-balance-due reply as the artifact: every claim in it reduces to a dollar amount and a transaction reference, both directly checkable against the ledger in code. That is what let the verifier be pure code, no second model call needed to judge correctness, which is the design this whole build leans on.
- Used Claude Code throughout this build for implementation, with every scope call, mechanism choice, and cut made and directed personally: which artifact to build, which consumption mechanism, which stretch items, the labeling approach. Where this helped: fast iteration on live-model bugs, since each one needed a real run to surface. Where it needed correction: new ideas - like human vetoing - that were not in the brief, and the fact that the model was not perfectly reliable.
- The verifier is a real target, and its own tests caught three genuine bugs in it: a sentence splitter that merged the balance line into the next sentence and let a fabricated transaction slip through right after it; the same splitter breaking again once drafts used newline-separated bullet lists instead of prose, letting a wrong amount hide behind correct amounts elsewhere in the same merged block; and a model that occasionally echoed its own revise-feedback text into the client-facing draft, which the verifier missed until a marker-based check was added. All three are fixed with regression tests.
- Found that a technically "grounded" draft can still be a bad one: a model producing a near-empty, content-free summary passed the verifier (nothing false in it) but was a poor client message. Fixed by having the simulated human decline any approved draft with zero transaction citations, and by making retrieval memory independently enforce the same floor, so a sparse draft can neither get logged as approved nor teach future drafts. Also had to make itemization mandatory in the prompt rather than conditional, since the model reliably found the easy compliant path of saying nothing specific once memory or retries were in play.
- Added a second synthetic client specifically to test something a single-client fixture cannot: whether retrieval memory respects client boundaries. It did not at first, `get_approved_examples` had no client filter at all. This is the most important bug found in the whole build, exactly the kind a real multi-tenant system like Maxed's would care about most, and exactly the kind of bug a minimal fixture set structurally cannot surface. Fixed by scoping retrieval to client id, verified with both a direct unit test and a full integration test running the real learning cycle for both clients against one shared log.
- Judge computes factual_grounding and absence_of_invented_numbers entirely in code from the same verifier critique, never asking the model, to handle numbers by code not model for the judge as well as the verifier. For the defended failure mode, anchoring the completeness rubric to a specific, checkable criterion (itemized citations) instead of a vague "how complete does this feel" is what stops length-padding attacks from moving the score, shown by a live, direct comparison against a deliberately naive version of the same prompt.
- The calibration and before/after numbers are not stable to two decimal places on this scale. Across three live runs of the same 12-draft calibration set, tone correlation measured 0.75, 0.46, and 0.06; length-bias comparisons ranged from the anchored prompt clearly outperforming the naive one to showing no difference at all; one before/after run improved, another declined. The two code-derived dimensions never moved between runs, only the two model-scored ones did. Reporting the full range rather than the friendliest single run is the honest choice here, not a weakness to hide.
- Built two of five brief-listed stretch items, both analysis over data the core build already produces rather than new generation machinery: calibrating abstain versus escalate (validates that escalate corrections resolve cleanly, and shows what is really driving abstention), and preference dataset construction from the decision log (real `{prompt, chosen, rejected}` triples, shaped for a DPO pass). Did not attempt running the fine-tune itself: this machine took roughly 5 minutes per single `gemma2:9b` inference call, CPU only, no GPU, and an actual training run was a real risk to the clock rather than a reasonable bet.
- "One idea we did not ask for" - a human veto on individual memory examples: approving a draft ("send this") and endorsing it as a teaching example ("copy this style forever") are different decisions the system was silently treating as one. Built rather than only proposed, since the mechanism was small: an id and a `memory_veto` flag on every decision record, a `list-decisions` and `veto-memory` command, one added line in the retrieval filter. Live-verified end to end: 4 eligible examples before vetoing one, 3 after, an unknown id correctly rejected.
- What I know now that I did not at start: the verifier's regex-based approach is more robust than expected against edge cases tried deliberately (thousand separators, negative notations, markdown tables), but genuinely fragile against anything that changes the text's structural shape (newlines instead of periods, echoed feedback), which is a more useful distinction than "regex is risky" in the abstract. The other is that a metric can move in the right direction for the wrong reason, attempts-to-settle improved once purely because the model learned to say less, and the only way to catch that was checking the raw drafts, not the summary table.
