# Decision journal

## 2026-07-18

- Chose the client-balance-due reply as the artifact for Part 1: every claim in it reduces to a dollar amount and a transaction reference, both of which are directly checkable against the ledger in code. That made the verifier fully deterministic, no second model call needed to judge correctness.
- Designed the generation prompt to require a transaction id in parentheses next to every dollar amount, and a fixed `Total balance due: $X` closing line. This turns "does the draft match the records" into a regex-and-lookup problem instead of a natural-language-understanding problem, which is what let the verifier be pure code rather than a second, fuzzier model call.
- Verifier bug found by its own injected-error test: the balance line had no trailing punctuation, so a naive sentence splitter merged it with the next sentence, and a fabricated transaction cited right after the balance line was skipped because the merged sentence matched the "already checked the balance" guard. Fixed by stripping only the matched balance substring from the text before splitting, instead of skipping any sentence that merely contained it. Caught 2 of 5 injected-error cases as false negatives before the fix, 5 of 5 after.
- Correctable issues (wrong_amount, wrong_balance, where a real record exists but a number is off) route to escalate. Uncorrectable issues (fabricated_transaction, unsupported_claim, missing_balance, where nothing in the ledger supports the claim at all) route to abstain. This split is a fixed rule for this build, not learned; calibrating it is listed as stretch in the brief.
- gemma2:9b via local Ollama produced a fully correct draft on the first attempt against the real fixture ledger (all 28 transactions, correct citations, correct balance), but took close to 5 minutes for that single call on this machine. Too slow to run repeated batches in the learning-cycle demo, so switched to gemma2:2b for batch runs and noted the tradeoff rather than quietly working around it.
- gemma2:2b is roughly 3.5x faster per call than 9b on this machine, but its draft truncated the transaction list partway through instead of covering all 28. It still passed the verifier (approved) because the verifier only checks that whatever is claimed is grounded, not that everything is covered. That is a real gap between Part 1 and Part 3: grounding and completeness are different properties, and a draft can score perfectly on one while failing the other. Completeness is a judge dimension in Part 3, not something Part 1's verifier is meant to catch.
- First live learning-cycle run (gemma2:2b, batch size 3): average attempts to settle went from 1.33 (batch 1, no memory) to 1.00 (batch 2, with retrieval memory of batch 1's approved examples), all 6 drafts approved, none escalated or abstained. Checked the actual logged drafts rather than trusting the summary number: batch 1's three drafts cited 0, 0, and 3 real transactions respectively (the one with 3 citations is the one that needed a revision). All three batch 2 drafts cited zero transactions, one of them only 33 characters long. The verifier does not require a minimum amount of grounded detail, only that whatever is claimed is true, so a nearly empty draft is trivially easy to get approved. The drop in average attempts for batch 2 most likely reflects the model copying the minimal, low-detail style of the two content-free examples in its retrieval memory, not becoming more accurate. Attempts-to-settle alone is not evidence that batch 2 is a better client-facing message, and reporting it without this check would have been an unsupported claim of improvement. This is a real gap in Part 1's verifier by design (it checks grounding, not completeness) and it is the concrete, measured reason Part 3's judge needs a completeness dimension rather than relying on the verifier's pass or fail as the only signal.
- Went back and fixed the sparse-draft gaming rather than only noting it, since it directly corrupts the learning signal: `human_sim` now declines any loop-approved draft that cites zero transactions instead of rubber-stamping it, and `retrieval_memory` independently enforces the same minimum-citation floor before accepting an example, so a sparse draft can neither get logged as approved nor enter memory even if the decline path had a gap elsewhere.
- Strengthened the generation prompt from "cite a transaction id when you mention one" (conditional, easy to satisfy by mentioning nothing) to "you must individually mention every transaction in the ledger" (mandatory). Without this, gemma2:2b reliably produced a one-line balance summary with no itemization at all, run after run, once memory injection or retries were in play. That is not an isolated fluke, it reproduced across two separate batch runs with different batch sizes.
- Found a second, more serious verifier bug from the richer, itemized drafts the strengthened prompt started producing: the sentence splitter only broke on `.`/`!`/`?`, but the model's bulleted list format has no punctuation between lines, so a full 28-line itemized list was treated as a single sentence. A wrong amount on one bullet line could then be masked because some other, correct amount elsewhere in the same giant merged "sentence" happened to satisfy the `any(...)` match check. Fixed by splitting on newlines first and only then on sentence punctuation within each line. Added a regression test with two wrong amounts on separate bullet lines, both now caught independently.
- Also found that `human_sim`'s escalate path only corrected the first issue in `critique.issues` via `_apply_correction`, silently leaving any additional wrong amounts uncorrected in what then got logged and reused as a human-approved example, actively teaching future drafts to repeat a real error. Fixed to loop over every issue and apply every correction before logging.
- Found a third failure mode directly from a live run: the model sometimes echoed the revise-feedback text verbatim into its own output ("Your previous draft had the following problems: ..."), leaking internal critique content into what is supposed to be a client-facing message. The verifier missed it because the echoed numbers had no dollar sign, so the amount regex never matched them. This is not a grounding problem, it is a presentation and leakage problem, and it would have been graded as a valid, learnable example without a fix. Added a deterministic marker-based check (`leaked_internal_text`, uncorrectable) and reworded the feedback preamble to explicitly tell the model not to repeat it.
- After all five fixes (sentence-merge masking, sparse-draft gaming closed on both the decline and memory sides, mandatory itemization, newline-aware splitting, multi-issue correction, leaked-feedback detection), re-ran the live learning-cycle once more: batch 1 and batch 2 came out identical (1.33 average attempts, 3 approved, 0 escalated, 0 abstained, both sides). No measurable movement in this run. Reporting that honestly rather than re-rolling until a bigger number appears: batch size 3 is a small sample, and the retrieval-memory mechanism only had one qualifying example to inject this time. The mechanism is demonstrably working correctly now (no gaming, no corrupted examples), but this specific run does not show it moving the needle, and that is a legitimate result to report as-is.
- Added a second synthetic client (Marlow and Finch Design Studio, CLIENT-002, its own 20-transaction ledger, balance $735.00, transaction ids continuing globally from TXN-029 so client 1 and client 2 ids can never collide) specifically to test something a single-client fixture cannot: whether retrieval memory respects client boundaries. It did not. `get_approved_examples` had no client filter at all, only a recency window over the whole shared decision log. With two clients writing to the same log, client 1's approved examples would have been eligible to leak straight into client 2's few-shot prompt. This is exactly the kind of bug a single-client fixture set structurally cannot surface, and exactly the kind of bug that matters most for a real multi-tenant system like Maxed's.
- Fixed by making `client_id` a required argument to `get_approved_examples`, filtering the log by it before any recency or quality filtering happens, and threading `client_id` through `run_learning_cycle` and the CLI (`--client-id` on `generate`, `injected-errors`, `learning-cycle`). Added both a direct unit test (two approved records for two different clients in one log, asking for client 2's examples must never return client 1's) and a fuller integration test that runs the actual learning cycle for client 1, then for client 2 against the same shared, non-reset log, and asserts none of client 1's transaction ids appear anywhere in client 2's injected memory block.
- Noted while fixing this: the verifier itself would have caught a leaked transaction id secondhand, as a `fabricated_transaction` (client 2's ledger does not contain client 1's ids), so there was already partial, accidental defense in depth. It would not have caught leaked style or client-name references with no transaction id attached, which is the real reason the fix belongs in retrieval memory directly rather than being left to the verifier to clean up after the fact.
- Also added six verifier edge-case tests directly (thousand-separator amounts, three negative-amount notations, several distinct issue types present in the same draft at once, an amount landing immediately before a sentence-ending period, and a wrong amount inside a markdown table row), specifically instead of enlarging the live batch size for the learning-cycle demo. All six passed against the existing implementation with no code changes needed; the abs-value comparison and newline-first splitting already handled them. Chose this over a bigger live batch because these are free (no model calls, deterministic) and directly test the verifier's actual grounding claim, while a bigger batch mostly just costs wall-clock time without adding much to what a batch of 3 to 5 already demonstrates. The real statistical weight for "did it improve" belongs in Part 3's hand-labeled set, not here.
- Started Part 3 with `judge.py`: factual_grounding and absence_of_invented_numbers are computed entirely in code from the same verifier critique, never asked to the model, specifically to keep "numbers by code, not by model" true for the judge as well as the verifier. Only completeness and tone go to the model, and the prompt anchors completeness to a specific, checkable criterion (itemized transaction citations) rather than leaving it as a vague "how complete does this feel."
- Tried to demonstrate length bias (the defended judge failure mode) against that same anchored prompt using three escalating attacks: generic pleasantry padding, literal duplication of the whole draft, and padding that explicitly asserts thoroughness. None of the three moved the score at all, live against gemma2:2b. Rather than force a result, tested why: built a second, deliberately naive judge prompt with the vague "how complete does this feel" wording the anchored one avoids, and ran the same sparse-draft-plus-thoroughness-padding pair against it. The naive prompt inflated completeness by 2 and tone by 1 purely from padding with zero new checkable facts; the anchored prompt showed a zero gap on the identical pair. This is a stronger, more honest result than the one originally planned: instead of bolting a defensive instruction onto a prompt after finding bias in it, it shows the specific design choice already made (anchoring completeness to itemized citations instead of a vague feeling) is the reason the bias does not appear, with a live, direct naive-versus-anchored comparison as evidence.
- Built a 12-draft calibration set (`data/eval/labeling_candidates.json`) deliberately spanning quality tiers the brief's own core cases plus a few more: one clean, fully-grounded draft; the four injected-error types from Part 1 (wrong amount, fabricated transaction, unsupported claim, wrong balance); three sparse-to-partial coverage drafts; a padded-filler draft; a leaked-internal-text draft; a factually perfect but unprofessionally-worded draft; and a compound draft with two distinct issues at once. Chose this spread specifically so every dimension (including tone, which nothing else in the set exercised much) would have real variance to correlate against.
- Asked whether to hand-label these myself before running calibration, since the brief's calibration step is explicitly about measuring the judge against a real human's judgment, not against another AI's. Given time constraints, labeled all 12 myself as a first pass instead, reading each draft independently against the same four-dimension rubric the judge uses rather than reverse-engineering what the code or model would say. This is disclosed plainly here and in the README: the calibration numbers below measure the judge against a careful rubric-following pass I did on the candidate's behalf, not against the candidate's own independent judgment. The candidate can replace `data/eval/human_labels.json` with their own labels before submission; the file and the calibration command are already wired to pick up whatever is there.
- First live calibration run (ad hoc script, all 12 drafts): Spearman correlation of 0.87 (factual_grounding), 0.99 (absence_of_invented_numbers), 0.76 (completeness), 0.75 (tone). Ran the actual `maxed-agent calibration` CLI command afterward as a live-verification step, expecting to reproduce roughly the same numbers, and got 0.87, 0.99, 0.58, and 0.46 instead, same 12 drafts, same labels, same model. The two code-derived dimensions were stable between runs since they never touch the model; the two model-scored dimensions moved noticeably. This is real run-to-run variance from the model's own sampling stochasticity on a 12-item set, not a bug, and it is itself a legitimate limitation to disclose: with only 12 labeled drafts, the completeness and tone correlation numbers are not stable to two decimal places, only to the extent that both runs agree the correlation is positive and moderate to strong. A larger labeled set would narrow this, and is exactly what the brief's own 10 to 20 range is a floor for, not a target. Reporting the CLI run's numbers (0.87, 0.99, 0.58, 0.46) as the reproducible figure, since that is what running the command in this repo actually produces.
- Both calibration runs should be read as measuring the judge against a careful rubric-following pass done in my (the assistant's) place, not against the candidate's own independent judgment, since the candidate has not yet hand-labeled the set themselves. Disclosed in the README as well. `data/eval/human_labels.json` can be replaced with the candidate's own labels before submission; the calibration command already picks up whatever is in that file with no code changes needed.
- Live `before-after` run (batch size 3, gemma2:2b, all the sparse-draft and multi-issue fixes from earlier in place): overall judge average moved from 4.25 to 4.58. factual_grounding and absence_of_invented_numbers stayed at a perfect 5.00 in both batches, no false claims either side. The movement came entirely from completeness (3.00 to 3.67) and tone (4.00 to 4.67). Checked the raw drafts before trusting this: one batch 2 draft showed 56 raw "TXN-" substring matches against a 28-transaction ledger, which looked like it might be the same kind of echo bug found earlier with leaked revise-feedback, this time possibly leaking the few-shot memory examples into the output. Checked directly: the model had just cited each transaction id twice per line (once as the bullet label, once in parentheses per the citation-format instruction), and the verifier found zero issues with 28 of 28 distinct transactions correctly cited. A real, legitimate, fully-grounded improvement, not a measurement artifact, this time with the anti-gaming fixes already in place to back it up.
- Ran the `maxed-agent length-bias` CLI command as a live-verification step, expecting to roughly reproduce the earlier naive-versus-anchored finding. Direction held: naive showed a completeness and tone gap of 1 and 1, anchored showed 0 and 1. The anchored prompt did not repeat the earlier clean zero-and-zero result on tone specifically this time, same underlying cause as the calibration variance already noted, model sampling stochasticity on a single comparison pair. The finding as reported in the README is now phrased as "reduces, and on one run eliminated" rather than claiming a guaranteed zero every time, since that is what was actually observed across two runs.
